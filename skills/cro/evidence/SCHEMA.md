# CRO evidence records

One UTF-8 JSON object per `tests/<id>.json`. No source URL means no record.
Run `"<CRO_SCRIPTS>/cro-py" evidence.py validate` before and after changes.
The executable validator is `../scripts/evidence.py`; this document defines meaning.

## Fields

All fields in this table are required, even when their value is null.

| Field | Format and meaning |
|-------|--------------------|
| `id` | Unique lowercase hyphenated slug, equal to the filename without `.json`. |
| `title` | Short factual description of the experiment. |
| `company` | Business whose experience was tested, not the reporting agency. Use an explicit anonymous description if undisclosed; expect verification to remain unverified. |
| `industry` | Plain-English industry. |
| `business_type` | Exact primary type from `../references/business-types.md`. That file is the only vocabulary authority. |
| `page_type` | Lowercase label. Seed vocabulary: `home`, `landing`, `product`, `category`, `pricing`, `cart`, `checkout`, `lead-form`, `global`. |
| `element` | Specific lowercase hyphenated label, such as `testimonials`, `form-fields`, `cta-copy`, `price-comparison`. |
| `change` | Object with nonempty `control` and `variant` descriptions. Describe everything changed together. |
| `result` | Object with `metric`, `relative_lift_pct`, `direction`, and optional `desired_direction`. See below. |
| `sample_size` | Published count object or null. |
| `conversions` | Published count object or null, with the conversion event in `unit`. |
| `significance` | Published significance object or null. |
| `test_duration` | Published duration as text, for example `22 days` or `over 5 months`; otherwise null. |
| `date_published` | Source's original publication date as `YYYY-MM-DD`, otherwise null. Never use a sitemap modification date as publication. |
| `source_url` | Required absolute HTTP(S) source URL without credentials. Prefer the original account, not a roundup. |
| `source_type` | `company blog`, `agency case study`, `academic`, or `platform case study`. |
| `quote` | Short exact visible-text excerpt supporting the recorded result. Preserve numbers, roundings and qualifications. |
| `verification` | `verified` or `unverified`, maintained by `verify`. |
| `evidence_strength` | `A`, `B`, or `C`, independently of verification. |
| `principles` | Nonempty array of unique lowercase hyphenated tags, such as `social-proof`, `friction`, `clarity`, `urgency`. |
| `added_date` | Date this record was added, `YYYY-MM-DD`. |
| `added_by` | Contributor name or research-run identity. |

Optional fields:

- `research_type`: `ab-test` (default) or `research`. Baymard usability research
  is `research`, never an A/B test. Do not invent a control or variant: describe
  the observed comparison and its limits. Exclude these from A/B-test counts.
- `notes`: qualifications, population/device, conflicting headline/body numbers,
  metric ambiguity, sequential stopping, business-model classification, and limits.
- `verification_details`: generated by `verify`, never supplied as proof by `add`.

### Results

```json
{
  "metric": "completed purchases",
  "relative_lift_pct": -3,
  "direction": "loss",
  "desired_direction": "increase"
}
```

Lift is a **signed relative percent**, not percentage points and not an absolute
conversion rate. `12` means +12%, not 0.12%. Preserve the publisher's reported
precision; do not recompute from rounded displayed rates. A decrease can be a win
for a cost metric: use `desired_direction: "decrease"` and a negative lift.

`direction` is `win`, `loss`, or `flat`. Flat also covers explicitly inconclusive
results. It never means proven equivalence. Keep a published nonsignificant
point estimate if available, explain it in notes, and use `flat`. Without a
numeric estimate use null, not an invented zero. Record the metric and population
exactly: clicks are not sales, mobile is not all traffic, and trial losses can
coexist with revenue wins. One record represents one comparison, not one metric;
put secondary metrics in notes rather than duplicating a comparison.

### Counts and significance

```json
{
  "sample_size": {"control": 1950, "variant": 1925, "unit": "visitors"},
  "conversions": {"control": 135, "variant": 100, "unit": "trial signups"},
  "significance": {"confidence_pct": 95, "p_value": null, "reported": "95% confidence reported by publisher"}
}
```

Count objects accept `total`, `control`, `variant` as nonnegative integers, plus
`unit` for interpretation. At least one count must be present. Do not infer arm
counts from an approximate split. A source saying "over 12,100" is stored as a
lower bound with that qualification in `unit` and notes, not an exact count.
Confidence is in 0-100; p-value is in 0-1. Do not derive one from the other.
A qualitative significance claim may have both numeric fields null but must
have a `reported` description. A planning significance threshold alone is not
an achieved result. Preserve a publisher's rounded "100%" with a caveat; it is
not certainty. Never calculate missing significance from a lift alone.

### Strength and verification are different

- **A:** Numeric lift, sample size and significance published. This is a reporting
  completeness grade, not a guarantee of design quality or adequate power.
- **B:** Numeric lift published but sample size or significance missing.
- **C:** Qualitative/anecdotal result, including no published lift.

`verify <id>` fetches via `fetch_page.fetch_page`, including its private-address
and per-redirect checks. It rejects non-2xx, blocked and effectively empty pages.
It checks visible text for the company, the numeric percent and the exact quote;
the numeric percent must also occur in the quote. Scripts/styles are excluded.
`verified` means these checks passed, not that the experiment was replicated or
its causal conclusion proved. A page with no published lift remains unverified
even when its qualitative quote is confirmed. Honest unverified records can be
kept if the source loads; unreachable sources are not eligible for the seed.

Generated details include UTC `checked_at`, `source_loaded`, `status_code`,
`final_url`, `company_found`, `lift_found`, `quote_found`, `fetched_with`, a hash
of the visible text, and a reason. A failed fetch overwrites stale verification
with unverified. `add` always resets verification and discards submitted details.
The fingerprint detects later changes; it is not an archived copy of the page.

## CLI

Use the installed wrapper, with `--db` **before** the command if overriding the
folder. Default database is resolved relative to the installed script, not CWD.

```bash
"<CRO_SCRIPTS>/cro-py" evidence.py validate
"<CRO_SCRIPTS>/cro-py" evidence.py add candidate.json
"<CRO_SCRIPTS>/cro-py" evidence.py verify <id>
"<CRO_SCRIPTS>/cro-py" evidence.py verify all --timeout 30
"<CRO_SCRIPTS>/cro-py" evidence.py search --business-type "SaaS" --page-type pricing --element pricing-table --principle clarity --min-strength B
"<CRO_SCRIPTS>/cro-py" evidence.py search --page-type product --json
"<CRO_SCRIPTS>/cro-py" evidence.py stats
"<CRO_SCRIPTS>/cro-py" evidence.py export-md
```

Search filters are exact, case-insensitive, and combined with AND. Minimum B
includes A and B; minimum A includes only A. Results include status and source.
Use `--json` for structured findings and citation generation. Zero matches is
not an error. `verify` returns nonzero for source-load failures or invalid IDs;
a loaded page with unmatched claims returns zero with explicit unverified status.
Always inspect that status, not just the process exit code.

Duplicates are detected by normalized source URL plus control/variant text.
Fragments and common tracking parameters are ignored. Different comparisons on
the same page are allowed. Paraphrased changes, syndicated URLs and historical
redirect aliases still need manual deduplication. `add` refuses duplicate IDs and
does not overwrite records. Use one writer per database; atomic file replacement
prevents partial JSON, not concurrent claim races.

## Catalog, legacy and bias

`export-md` regenerates `CATALOG.md`, grouped by page type and sorted by ID.
The JSON files are the source of truth. The legacy `proven-tests-*.md` files have
no source URLs: they are **unverified idea lists**, not migrated evidence.

Published wins are heavily overrepresented. Seek losses and null results on
every research run. The initial seed deliberately includes three observed losses
and two qualitative/inconclusive results. Some records describe different variants
or earlier rounds from one publication; record counts are not independent-study
counts. External results motivate hypotheses, never promise a lift on a client site.
